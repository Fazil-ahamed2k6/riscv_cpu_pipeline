# 32-bit RV32I Pipelined RISC-V Processor

### RTL → GDSII Physical Design | Sky130A | OpenLane2

A 32-bit RV32I RISC-V processor designed, verified, and physically implemented through the ASIC RTL-to-GDSII flow.

## 🏗️ Architecture

The processor uses a pipelined datapath to reduce the amount of combinational logic traversed within a single clock cycle.

```text
              ┌──────────────────┐
              │ Instruction      │
              │ Memory           │
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ Decode /         │
              │ Register File    │
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ Execute / ALU    │
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ Memory Access    │
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ Write Back       │
              └──────────────────┘
```

The major processing stages are:

```text
Instruction Fetch
        │
        ▼
Instruction Decode
        │
        ▼
Execute
        │
        ▼
Memory Access
        │
        ▼
Write Back
```

Pipeline registers separate the major stages and store intermediate data and control information.

## 🛠️ Development Journey

The processor was developed incrementally, with both functional correctness and physical implementation considered during development.

### 1. Initial Architecture

The processor was initially developed as a non-pipelined design. Timing analysis showed a significant setup-timing limitation, with approximately **-20 ns setup slack**.

### 2. Architecture Analysis

The datapath was analyzed to identify major combinational-delay contributors, including ALU logic, control logic, register selection, forwarding paths, and memory-address generation.

### 3. Pipelined Processor

The architecture was redesigned into a pipelined processor using pipeline registers between the major datapath stages.

### 4. Forwarding and Hazard Handling

Data dependencies introduced by pipelining were addressed using forwarding logic and hazard detection.

### 5. RTL Verification

The processor was functionally verified using Icarus Verilog before and during physical-design iterations.

### 6. Physical Implementation

The verified RTL was taken through synthesis, floorplanning, placement, CTS, routing, post-layout STA, physical verification, power analysis, and GDSII generation.

## 🔄 Pipeline Operation

The processor allows multiple instructions to occupy different pipeline stages simultaneously.

```text
Cycle       I1       I2       I3       I4
-------------------------------------------
1           IF
2           ID       IF
3           EX       ID       IF
4           MEM      EX       ID       IF
5           WB       MEM      EX       ID
6                    WB       MEM      EX
7                             WB       MEM
8                                      WB
```

This organization reduces the amount of combinational logic that must be completed within a single clock period compared with the initial non-pipelined architecture.

---

## 🔀 Data Forwarding

Pipeline execution introduces data dependencies between instructions.

For example:

```text
ADD x3, x1, x2
SUB x4, x3, x5
```

The second instruction requires the result generated by the preceding instruction.

The forwarding unit compares source and destination register identifiers and generates control signals that select the appropriate data source.

```text
                 EX/MEM Result
                       │
                       ▼
Register File ──► Operand MUX ──► ALU
                       ▲
                       │
                 MEM/WB Result
```

Forwarding allows required results to be supplied directly from later pipeline stages instead of unnecessarily waiting for register write-back.

---

## ⚠️ Hazard Detection

A pipelined processor must detect situations where instructions cannot safely proceed through the pipeline.

The hazard unit monitors relevant pipeline information and generates the required control behavior.

Hazard handling works together with:

- Pipeline registers
- Forwarding logic
- Register dependencies
- Control signals
- Operand selection

The objective is to preserve correct instruction execution while minimizing unnecessary pipeline disruption.

## 📉 Timing Optimization Journey

The initial architecture exhibited approximately **-20 ns setup slack**.

Architectural pipelining and iterative RTL and physical-design optimization substantially reduced the timing limitation.

Several experiments demonstrated that improving one metric did not necessarily improve the complete implementation.

```text
WNS improvement
      ≠
Overall timing improvement
```

An optimization could improve WNS while increasing TNS or the number of violating paths.

The final configuration was therefore selected based on overall timing behavior and implementation stability.

Detailed timing experiments can be documented under:


## 🧠 Key Technical Learnings

### RTL Structure Affects Timing
Different RTL descriptions of logically equivalent operations can synthesize into different gate structures and timing characteristics.

### Pipelining Reduces Logic Depth
Breaking a long combinational path into multiple stages reduces the amount of logic evaluated during one clock period.

### Forwarding Logic Can Become Timing-Critical
Forwarding improves pipeline efficiency, but register comparisons and operand-selection logic can introduce additional timing paths.

### Physical Implementation Affects Timing
Placement, routing, buffering, and interconnect delay become important contributors after synthesis.

### WNS Alone Is Not Sufficient
A design with improved WNS can still have worse overall timing if TNS or the number of violating paths increases.

Timing optimization therefore requires analysis of multiple implementation metrics.

## 🛑 Why Optimization Was Stopped

Several RTL and physical-design optimization experiments were performed.

Some modifications improved one timing metric while degrading others.

Examples:

```text
Better WNS
    ↓
Worse TNS
```

or:

```text
Reduced critical-path delay
    ↓
Additional violating paths
```

The final configuration was selected as a stable implementation with:

- Functional RTL verification
- Completed synthesis
- Completed physical implementation
- Positive hold slack
- DRC verification
- LVS verification
- Power analysis
- Final GDSII generation

Setup timing remains an identified area for future optimization.
